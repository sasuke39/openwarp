# 05-与现有模块的集成

## 1. 与系统提示词

在 `internal/agent/prompt.go` 的工具列表里加一项：

```
7. **update_task_list** - 更新任务清单。用于规划步骤、跟踪进度、保持专注。
   参数: tasks 数组,每个含 id/content/status/priority。
   规则: 最多一个 in_progress;每次传完整列表(覆盖)。
```

在"工作方式"里加一句：

```
5. 复杂任务先用 update_task_list 列出步骤,做完一步标一步。
```

## 2. 与 agent loop(main.go)

### 工具注册

`llm.go` 的 tools 数组里加 `update_task_list` 的 JSON schema(见 02-工具定义）。

### 工具路由

`runAgentLoop` 里 `sendToolCalls` 前加一个分支：

```go
case "update_task_list":
    // 校验 -> 更新 conv.todoList -> 返回成功/失败结果
    // 不进入 sendToolCalls(不需要客户端执行)
```

**关键区别**:update_task_list 是**服务端执行**的工具，不需要转发给 Warp 客户端/容器执行。它只改 adapter 内存里的状态。

### 每轮注入

`runAgentLoop` 每轮调 `StreamChat` 前，把 `conv.todoList` 格式化成"Current Task Progress"追加到 system prompt 尾部（和 `WithExecutionContext` 同一个位置）。

## 3. 与记忆系统

todoList 不进记忆。session notes 的"Workflow"节会自然包含 todo 进展（提取器会看到对话历史里的 todo 调用），但 todoList 本身不单独持久化。

原因：todo 是"当前任务的规划"，任务结束就没用了。跨会话的持久知识由项目记忆负责。

## 4. 与上下文压缩

压缩时 todoList 的状态会丢失（它不在 conv.history 里）。但 session notes 里的"Current State"和"Workflow"节会保留进展信息，所以压缩后模型能从 notes 恢复上下文。

todoList 本身不恢复（新一轮重新规划是正常的）。

## 5. 与 Warp 客户端 UI

Warp 客户端已有 todo 渲染逻辑（`plan_and_todo_list.rs` + `todos.rs`)，通过 `BlocklistAIHistoryEvent::UpdatedTodoList` 事件驱动。

adapter 需要把 todo 状态通过 protobuf 推给客户端。当前 proto 里有没有 todo 消息？查一下 `proto3/task.proto`:

- 如果没有，加 `Message_TodoList` 消息，包含 tasks 数组
- adapter 在校验通过后发 ClientAction 给客户端
- 客户端收到后渲染 todo 面板

**但这步可以先不做**--第一版只在 adapter 侧生效（模型行为改善），UI 展示作为后续增强。

## 6. 与评测

评测时 `update_task_list` 直接在 adapter 执行，不需要容器做什么。Harbor agent 不需要改。

评测新增指标：
- 每题 todo 总数 / 完成率
- 是否先列计划再动手
- "标 completed 但 reward=0"的比率（规划质量）
