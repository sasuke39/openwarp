# 01-设计动机

## 实测到的两类失败模式

从 Terminal-Bench 评测的 18 道题轨迹里，我们反复看到两类因为缺乏任务规划导致的失败：

### 模式一：反复探索不产出

- `path-tracing`(Kimi K3)：30 轮全在写 `probe1.py` 到 `fit7.py` 分析图片特征，**没写一行题目要求的 `image.c`**
- `cobol-modernization`(GLM-5.2)：16 轮全在理解 COBOL 边界行为，**没写一行 Python 代码**，最后一轮还在说"我现在彻底理解了"

模型陷入了"无限探索"陷阱，没有判断"我已经理解够了，该开始产出"的能力。

### 模式二：走偏方向不自知

- `db-wal-recovery`(GLM-5.2)：WAL 文件被 SQLite 删了后，模型花 17 轮试图从容器层恢复文件，**完全偏离了"解析 WAL 文件格式"这个正确方向**

模型没有"停下来想想我现在在做什么"的机制，一条路走到黑。

## 业界的答案

Claude Code / Cursor / Cline 等主流 agent 都用同一个解法：**TodoWrite 工具**。不是提示词里建议"请列计划"，而是给模型一个结构化工具，强制它把计划写出来、逐步打勾。

效果：
- 模型必须先想清楚步骤再动手 -> 治"没想清楚就乱试"
- 每次工具调用后 todo 状态重新注入 -> 模型不会忘记当前在做什么 -> 治"走偏不自知"
- 全部 completed 才能结束 -> 治"探索完了不产出"

## 我们为什么不能只在提示词里写

现在的提示词有一句"第一次调用工具前，先用一两句话说清你打算怎么做"——这是**软约束**，模型可以说一句"我打算先看看"然后继续乱来。

软约束 vs 硬工具的区别：

| | 提示词建议 | 工具 |
|---|---|---|
| 约束力 | 模型可忽略 | 模型必须调，不调就没工具结果 |
| 结构化 | 自由文本，无法校验 | JSON schema 强校验（单 in_progress) |
| 状态可见性 | 说完就忘 | 每轮重新注入，始终可见 |
| 可度量 | 无法量化 | 可以统计"每题平均 todo 数 / 完成率" |

## 预期收益

1. 治 path-tracing/cobol 式"无限探索不产出"
2. 治 db-wal 式"走偏不自知"
3. 治 crack-7z 式"没规划就装工具走弯路"
4. 给后续优化提供数据基础（每题的 todo 完成率、平均每题步数）
