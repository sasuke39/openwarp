# 04-状态覆盖与结束判定

## 覆盖语义详解

`update_task_list` 是**全量覆盖**，不是增量。每次调用传完整列表，服务端直接替换。

### 为什么选覆盖不选增量

| | 覆盖（全量传） | 增量（只传变更） |
|---|---|---|
| 模型负担 | 每次要传全部（可能几十条） | 只传改的那几条 |
| 服务端逻辑 | 极简：直接替换 | 复杂：merge/冲突处理 |
| 一致性 | 模型负责，服务端只校验 | 容易出现"服务端状态和模型想的不一样" |
| 改计划 | 直接传新列表 | 需要额外的 delete/reorder 操作 |

Claude Code 也是覆盖。模型传几十条也就多几百 token，远小于一致性出问题的代价。

### 覆盖时的校验细节

覆盖前校验新列表：
- id 唯一
- 最多一个 in_progress
- 每个 task 有合法 status

覆盖后：
- 之前 completed 的如果被新列表删掉了 -> 保持删除（模型改计划是允许的）
- 之前 in_progress 的如果被新列表标成 pending -> 允许（模型想暂停当前做别的）
- 之前 completed 的如果被新列表改回 pending -> 允许（模型发现没做完，回滚）

不限制任何状态回退--模型对自己的计划有完全自主权。

## 并发安全

一个 conversation 只有一个 agent loop 在跑（`conv.mu` 互斥），所以 todoList 的读写天然串行，不需要额外锁。

跨 conversation 不共享（每个 conversation 有自己的 todoList)。

## 结束判定

**核心规则：todo 列表存在且全部 completed -> 模型可以输出最终答案并结束。**

但这不是硬限制：

- 模型可以在 todo 全部 completed 之前就输出最终答案（比如它发现题目做不了，决定放弃）。不拦。
- 模型也可以在 todo 全部 completed 后继续说话（比如补充说明）。不拦。
- todo 只是规划工具，不是执行审计器。

### 结束判定的用途

主要用于**评测分析**：统计每道题的 todo 完成率（完成数/总数）、平均每题轮数、以及"标 completed 但实际没做对"的比率。这些数据能告诉我们模型的规划质量。

## 一个典型任务的完整生命周期

```
轮1: LLM 调 update_task_list([step-1:pending, step-2:pending, step-3:pending])
     -> adapter 校验通过,conv.todoList = [step-1, step-2, step-3]
     -> 下一轮 system prompt 尾部注入"3 pending tasks"

轮2: LLM 调 update_task_list([step-1:in_progress, step-2:pending, step-3:pending])
     -> adapter 校验通过
     -> 下一轮注入"step-1 in_progress, step-2 pending, step-3 pending"

轮3: LLM 调 read_files(读代码)
     -> 工具结果返回
     -> 下一轮注入同上(状态没变)

轮4: LLM 调 update_task_list([step-1:completed, step-2:in_progress, step-3:pending])
     -> adapter 校验通过
     -> 下一轮注入"step-1 completed, step-2 in_progress, step-3 pending"

轮5: LLM 调 apply_file_diffs(写修复)
     -> 工具结果返回
     -> 注入"step-1 completed, step-2 in_progress, step-3 pending"

轮6: LLM 调 run_shell_command(跑测试)
     -> 工具结果返回(测试通过)
     -> 注入同上

轮7: LLM 调 update_task_list([step-1:completed, step-2:completed, step-3:completed])
     -> adapter 校验通过
     -> 注入"全部完成"

轮8: LLM 输出最终答案"修好了,改了 xxx 文件,测试通过"
     -> 没有工具调用,finish -> agent 结束
```
